## 1. Overview

Two bookkeeping tickets, both written when the plgg-ir-thesis work was still in
flight, and both overtaken by it. One asked whether the
`build-the-plgg-ir-thesis-evaluator` mission's progress still reflected reality;
the other was a session handoff pointing a fresh agent at a **red** worktree.
By the time this branch opened, the work had merged and the mission read 10/10.

The branch's actual content is therefore verification, not change: proving the
claims before acting on them, then closing what was genuinely finished and
explicitly deferring what is not this run's to decide. No code changed.

**Highlights:**

1. The mission's 10/10 acceptance was checked against merged `main` by building
   the chain from source and running its own proof binary — not by reading the
   checklist.
2. `build-the-plgg-ir-thesis-evaluator` closed `achieved` (267 tests green).
3. The resume checkpoint's five threads were each re-verified; three were already
   resolved, two are deferred planning decisions.
4. Surfaced along the way: **all five active missions are currently invisible to
   `/drive`** for a frontmatter-schema reason unrelated to their progress.

## 2. Motivation

`workaholic:implementation` / `objective-documentation` is the policy both
tickets answer to, and it is specifically about not accepting a count as its own
evidence. A mission whose acceptance list reads 10/10 because `archive.sh` ticked
each item as its ticket landed is *probably* complete — but "probably" is the
state the policy exists to eliminate, and closing a mission is the moment that
number becomes permanent.

The resume checkpoint carried the sharper version of the same problem. Its
acceptance — *"a fresh session can, from this file alone, enter the worktree,
understand the red state + fix, and drive the unification ticket to green"* —
was already unsatisfiable, because the red state it describes had been fixed and
merged. A handoff document's only value is that its claims are still true.

## 5. Historical Analysis

Both tickets were written 2026-07-21/22, one day before the work they describe
landed. That is the recurring shape here: a ticket that records *position* rather
than *requirement* is racing the work it describes, and it loses. The
`## Acceptance` marker convention and the `commit_hash`-is-derived-not-stamped
rule are earlier instances of the same lesson — a recorded fact about the repo's
state decays, so the repo itself has to be the source.

## 6. Concerns

- **All five missions in `.workaholic/missions/active/` are unclaimable by
  `/drive`.** `plan-units.sh` excluded every one as `not_approved`: they carry
  the legacy `status: active` + `drive_authorized: true` frontmatter, while the
  survey's floor is `status: approved`. Closing this one shrinks the set to four,
  but those four need `approve.sh` re-run — a developer act — before any run can
  claim them. From the survey's side, a fully-planned mission in this state is
  indistinguishable from one nobody wrote.
- **Two deferred planning decisions**, recorded rather than made: whether to
  ungate `modernize-plgg-test-for-concurrent-speed` (its own ticket says drive T1
  interactively first), and whether to replan or close the thin
  `grow-plggmatic-as-the-reference-framework` (0/0, no acceptance criteria).
- The `type: Mission` frontmatter mismatch above was found incidentally while
  surveying, not by any check. Nothing in `check-all` would catch a mission that
  silently stops being claimable.

## 7. Successful Development Patterns

- **Refusing to close on the checklist.** The mission read 10/10 and the close
  would have been correct — but the verification cost ~10 minutes of building and
  running, and it converted "the ticks say so" into "the proof binary prints the
  specified counterexamples". That is the difference the policy is asking for.
- **Driving a stale checkpoint as re-verification, not as instructions.** Reading
  its five threads as claims-to-check rather than steps-to-follow is what kept
  this run from entering a worktree looking for seven failing tests that no
  longer exist.
- **Deferring the two planning questions instead of resolving them.** Both had an
  obvious-looking answer (close the thin mission; ungate the gated one), and both
  are the developer's *what* rather than the executor's *how*.
