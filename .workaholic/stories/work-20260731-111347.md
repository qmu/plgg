## 1. Overview

`plggmatic@0.2.1` reached the npm registry with no `dist/` in the tarball. The
publisher had every fact it needed to refuse — the package declared
`main: "dist/index.es.js"` and staged nothing of the sort — but it asserted
nothing, so the defect surfaced only at the post-publish smoke test, after the
one step in the pipeline that cannot be undone.

This branch makes the publisher prove a tarball is complete **before** it
touches the registry.

**Highlights:**

1. A publishable package with no (or empty) `files` allowlist is now a hard
   preflight error, not a silently empty stage.
2. A staged tarball missing any path its own `main`/`types`/`exports`/`bin`
   declares aborts the run, naming the package and every missing path.
3. The checks run over the **whole publish set before the first publish** — the
   loop was split into stage-and-check-all, then publish-all.
4. Both shapes are covered by unit tests over pure functions, and both were
   proven end-to-end on the dry-run path without touching the registry.

## 2. Motivation

The root cause was narrow and worth stating precisely, because the obvious fix
would not have worked.

`stagePackage.ts` copies **only the package's `files` allowlist** into the
publish stage. `plggmatic` was the single publishable package with no `files`
field, so its `dist` was never staged and `publish.ts` shipped a tarball
containing little more than a README. What hid this is that a local `npm pack`
looks fine: npm's no-`files` default packs the entire directory, so the source
dir packs complete while the stage — the thing actually published — packs empty.
The two only disagree when the allowlist is missing, which is exactly the case
nobody was checking.

`workaholic:operation` / `ci-cd` names the situation this leaves behind: *"an
unverified release reaching production"*, with the decision to ship grounded in
a process turning green rather than in the artifact being right. An irreversible
step must be gated before it runs, not audited after.

## 3. Changes

### 3-1. Two pure predicates over a manifest ([24a3689a](https://github.com/qmu/plgg/commit/24a3689a))

`scripts/stagePackage.ts` gains `declaresStageAllowlist` and `entryTargets` /
`missingEntryTargets`, in the module's existing idiom: pure functions, no
filesystem, each unit-tested. `missingEntryTargets` takes an `exists` predicate
rather than reaching for `node:fs`, so the check is decidable in a test without
a stage on disk.

`entryTargets` walks every string leaf of `main`, `types`/`typings`, `exports`
and `bin` instead of pattern-matching a known shape — because there is no known
shape. This repo publishes three: `plgg` uses bare `import`/`require`
conditions with no `"."` key; `plggmatic` and `plggpress` use subpath keys over
condition maps; `plgg-bundle` is bin-only with no importable surface at all. A
reader assuming `exports["."]` sees nothing for `plgg`. `null` leaves (a blocked
subpath) and `*` patterns (a shape, not a file) are skipped as undecidable.

### 3-2. The publish loop split into two phases ([24a3689a](https://github.com/qmu/plgg/commit/24a3689a))

This is the part that makes the guarantee real, and it is why a per-package
check would not have sufficed. `runPublishSet` previously interleaved
stage → publish → stage → publish, so a check placed "before the publish" still
runs *after* every earlier package has already published. A defect in the fifth
package would be caught with four irreversible publishes already on the
registry.

The loop is now: stage and check **every** package, then publish every package.
A new `stageChecked` wraps `stageOne` with both assertions and throws a message
naming the package and the exact defect.

## 4. Outcome

Verified end-to-end on the `--dry-run` path, which never contacts the registry:

| Case | Result |
| ---- | ------ |
| Unbuilt `plgg` (stage missing its entries) | aborts, exit 1, naming `dist/index.cjs.js, dist/index.d.ts, dist/index.es.js` |
| Same package, once built | `staged → packed plgg-0.0.27.tgz (589.9 KB raw, 81.3 KB gz)`, exit 0 — unchanged |
| `plgg`'s `files` field removed (reverted probe) | aborts, exit 1, naming the package |
| `--only plgg,plgg-view`, `plgg` built and `plgg-view` not | aborts on `plgg-view` **without emitting `plgg`'s staged line** |

The last row is the acceptance that matters: under the old loop `plgg` would
have been published before `plgg-view` was ever inspected.

`node --test scripts/stagePackage.spec.ts` — 7/7 pass. The canonical scripts
typecheck (`tsc -p scripts/tsconfig.json`, the same invocation `check-all.sh`
runs) exits 0 with no `as`, `any`, or `ts-ignore`.

## 5. Historical Analysis

The repository already carried the lesson in a neighbouring form. `stagedManifest`
throws when a `file:` specifier survives the rewrite — the same instinct
(refuse to publish an unresolvable artifact), applied to dependency ranges but
never to the files themselves. This change extends an existing guarantee rather
than introducing a new kind of one.

The masking pattern is also familiar here: a local check passing while the real
artifact is broken is the same class as the sibling-dist masking `check-all.sh`
documents at its `gate-cross-runtime.sh` step, where a developer's tree carried
a dist the clean runner did not.

## 6. Concerns

- **The two-phase split is load-bearing and easy to undo.** A future assertion
  added inside the publish loop, rather than in the staging phase, silently
  narrows the guarantee back to "the first package is safe". Nothing in the test
  suite would catch that regression — the unit tests cover the predicates, not
  the loop's order. Worth a comment-level warning at minimum, which the code now
  carries.
- **Wildcard `exports` subpaths are deliberately unchecked.** `"./*": "./dist/*.js"`
  names a shape, not a path, so its existence is not decidable by this check. No
  package in the repo uses one today; if one starts, its entry points are
  outside the gate.
- **All 39 publishable packages currently declare `files`**, so the allowlist
  half of this gate is purely preventive on today's tree. It was verified by a
  reverted probe rather than by an existing defect.

## 7. Successful Development Patterns

- **Reach for the real failure state instead of fabricating one.** A freshly
  created worktree has no built dists, which *is* the "tarball missing its entry
  point" shape. The primary verification needed no mocking and no doctored
  fixture — just running the dry-run in a clean tree.
- **Prove the ordering claim, not just the check.** It would have been easy to
  stop at "the check fires". Running a two-package set with the defect in the
  *second* package is what actually demonstrates the fix's central claim.
- **Injecting `exists` kept the check pure.** The filesystem stays in
  `publish.ts`; `stagePackage.ts` remains a module of pure functions with unit
  tests, matching the split its own header docstring describes.
