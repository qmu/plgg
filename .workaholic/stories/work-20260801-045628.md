## 2. Motivation

A finished mission that is still `active` is not a cosmetic problem. From the
survey's side it is excluded as `no_tickets` — which is the same signal a mission
gives when its plan was never written. So a completed effort and an empty one are
indistinguishable without opening the file, and `/drive` carried four of them on
every tick.

## 5. Historical Analysis

Earlier in this same session the survey reported these four as `not_approved`,
and that was diagnosed as legacy `status: active` + `drive_authorized: true`
frontmatter against a `status: approved` floor. That diagnosis was correct at the
time of observation and is no longer the live condition: closing an *unrelated*
mission (`build-the-plgg-ir-thesis-evaluator`, commit `a32ca577`) migrated the
whole set to `status: approved` as a side effect, and the exclusion reason became
`no_tickets`.

The lesson is narrow and worth keeping: **an exclusion reason is a reading, not a
property.** Naming a root cause from one survey observation — without re-reading
the artifact after any mutator has run — can confidently name the wrong one.

## 6. Concerns

- **`20260719125328-measure-live-publish-under-60s.md` is unreachable by any
  unit, and that is now the intended state.** It is excluded as `mission_member`,
  but its mission `modernize-plgg-bundle` is already archived, so no mission unit
  will ever offer it and it will never surface as loose backlog either. Clearing
  the stale relation would make it claimable — and would directly contradict its
  own frontmatter, which reads `blocked: human-gated — requires a LIVE npm
  publish + 2FA; DO NOT drive autonomously`. It was therefore left alone. It is
  the developer's to run at a real `/ship`; it is not lost, but nothing automated
  will remind anyone of it.
- More generally, a ticket whose mission closes without it is **silently
  orphaned**. Nothing warns at close time that a mission is leaving a queued
  ticket behind with a relation that now points at an archive.

## 7. Successful Development Patterns

- **Reading the artifact before "fixing" it.** The obvious drive-readiness move
  was to clear the orphaned ticket's stale mission relation. Opening the file
  first showed a `blocked:` line explicitly forbidding exactly that outcome.
- **Closing through the mutator, four times, rather than editing four files.**
  `close.sh` writes the changelog line, flips the status, and moves the directory
  as one idempotent act; four hand-edits would have produced four chances to
  disagree with it.
