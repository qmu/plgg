# Fill the served content index from the corpus etc

## Summary

The served instance's MCP tools answered correctly and emptily, because nothing ever wrote a row into the content index they read. A corpus reader now runs at serve boot, so `search_content`, `get_article` and `list_collections` return the documentation the same instance renders.

## Key Changes

- A pure corpus mapping (`indexInputsOf`) plus the I/O shell over it (`ingestCorpus`), wired into the one place every downstream reader shares
- `collectPages` and `rawHtmlOf` published from plggpress, so the derived index is built by the SSG's own reader rather than a second corpus walker
- `healthWeb` reports the indexed document count, making "serving, but with nothing indexed" visible from outside
- A corpus that will not read or parse fails the boot instead of quietly serving an empty index

## Changes

### Added

- Boot-time corpus ingest for `plgg-cms serve`: the derived content index is rebuilt from the Markdown corpus on every start, and the delivery API, the MCP tools, the plugin export and the admin browser all read the filled index

### Changed

- `GET /health` now reports the indexed document count alongside its status
- `ROLLOUT.md` no longer files the empty content index under deferred deploy config; it was a missing code path, and a persistent DB path would not have added one document
- `agent-surfaces.md` gains the startup command it never carried, and states the `/mcp` auth posture that actually ships
