# Serve the guide from Cloudflare Workers with a staging surface

## Summary

The guide's delivery moves off GitHub Pages onto Cloudflare Workers, and gains the staging surface it never had. Production `plgg.qmu.co.jp` is now an assets-only Worker deployed on every merge to `main`; `staging-plgg.qmu.co.jp` is a second Worker over the identical build, marked noindex and visibly pre-production. The cutover was ordered so the live site never went dark.

## Key Changes

- Production is an assets-only Worker — no script, because a pre-rendered tree needs none; Static Assets already answers directory URLs and 404s
- `deploy-guide.yml` publishes through the guide's own `deploy` script; the two Pages actions and their `pages`/`id-token` grants are gone
- Staging forks off the same `dist/` as `env.staging`, the one environment with a script (`worker/staging.ts`: noindex header, disallow-all robots.txt, pre-production banner)
- Ownership split by resource: wrangler owns the routes, the corporate repository's Terraform owns the DNS records — no shared write, no deploy silently overwriting a Terraform-managed record

## Changes

### Added

- `packages/guide/wrangler.jsonc` — production Worker plus `env.staging`, with `html_handling: auto-trailing-slash` and `not_found_handling: 404-page` repeated verbatim per environment (wrangler does not inherit `assets`)
- `packages/guide/worker/staging.ts` — the staging-only response layer, with `run_worker_first: true` so it marks every page rather than only misses
- `packages/guide/tsconfig.json` — the guide enters the whole-repo typecheck gate for the first time

### Changed

- `.github/workflows/deploy-guide.yml` — one deploy step running `npm run deploy --prefix packages/guide`, authenticated by repository secrets rather than the workflow's GitHub identity
- Stale Pages topology corrected in `site.config.ts` and `plggpress/OPERATIONS.md`

### Removed

- The GitHub Pages publish path from the workflow (the repository's Pages setting is retired separately — it is a setting, not a file)

## Deployment Verification

- **DNS (corporate#16, applied 2026-08-19):** `plgg.qmu.co.jp` flipped to proxied with its CNAME target left on `qmu.github.io`, so Pages kept serving through the orange cloud until the Worker route existed — the live site never went dark. `staging-plgg.qmu.co.jp` created as a proxied `AAAA 100::`. Plan measured at `1 to add, 1 to change, 0 to destroy` with no drift on the zone's 14 imported records.
- **Production:** route `plgg.qmu.co.jp/*` → `plgg-guide` (id `ea7bade7…`). `/`, `/concepts/`, `/getting-started/`, `/packages/plgg/` all 200; `/no-such-page` 404. `x-github-edge-region` gone from the response — the Worker, not Pages, is serving.
- **Staging:** 200 with `x-robots-tag: noindex, nofollow, noarchive`, the pre-production banner, and a disallow-all appended to `robots.txt`. Universal SSL's `*.qmu.co.jp` covers the hostname (`CN=qmu.co.jp`, SAN `DNS:*.qmu.co.jp`) — no per-host issuance.
- **Three failed deploy attempts preceded the green one**, all the same cause: the repository's `CLOUDFLARE_API_TOKEN` carried only `Account / Workers Scripts / Edit`, and a `routes`-carrying deploy also needs `Zone / Workers Routes / Edit` on `qmu.co.jp`. Each failure uploaded the Worker and then refused the route, leaving Pages serving — the loud-failure design working as intended.
