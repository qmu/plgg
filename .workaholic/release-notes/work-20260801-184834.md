# Add AWS SigV4 request signing to plgg-fetch

## Summary

plgg-fetch can now sign an AWS request: canonical request, credential scope, the
four-link HMAC signing-key chain, and the `Authorization` header, as a
mostly-pure domain module over a second vendor seam holding the only contact
with Web Crypto. No SDK and no new dependency — hashing and HMAC are a platform
capability, not a package.

## Key Changes

- Verified against **AWS's own published test-suite vectors**, not against our
  own output: the canonical request matches byte-for-byte on all 20 cases of the
  suite's basic set.
- Two of AWS's twenty vectors contradict themselves (their `.sts` hash is not the
  SHA-256 of the `.creq` beside them). The fixture records that as derived data
  computed with an independent hasher, signature assertions apply to the other
  18, and a test pins the exemption to exactly those two names.
- The signing chain is lifted through one `tryCatch` instead of threading a
  `Result` error arm through six steps, removing five unreachable branches.

## Changes

### Added

- `sigv4Auth` — the header `Dict` to spread into an AWS request.
- `sigv4Sign` — the same, plus the canonical request and string to sign, because
  AWS echoes both in a `SignatureDoesNotMatch` response.
- `sigv4Instant`, `sigv4Pairs`, `sigv4PayloadHash`, and the pure pieces
  (`canonicalUri`, `canonicalQuery`, `signedHeaders`, `canonicalRequest`,
  `credentialScope`, `stringToSign`).
- `src/vendors/webcrypto.ts` — the package's second vendor boundary, the only
  module touching `crypto.subtle`.

## Notes

Path normalization is deliberately not applied: SigV4 makes it per-service and
S3 does not normalize, so normalizing here would corrupt S3 keys containing `.`
or `//` segments. Nothing is synthesized onto the request either — SigV4 signs
the message as sent, so the caller passes every header it will send.

Package coverage: 100% statements / 100% lines / 97.56% branches / 98.04%
functions against a 91% gate.
