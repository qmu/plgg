# 変更を作って検証する

このガイドの例はパッケージ名から公開 API をインポートします。[入門](/getting-started/)の手順でビルドしたら、各パッケージの `README.md` で使用例を、`src` で実装と `*.spec.ts` の入力例を確認できます。たとえば `packages/plgg` で `npm test` を実行すると、基本の型と関数のテストが動きます。

## 型検査とテストを使い分ける

リポジトリ直下で `sh scripts/tsc-plgg.sh` を実行すると plgg 本体を型検査します。`node scripts/typecheck.ts plgg-router` のように名前を渡すとそのパッケージを、名前を省くと全体を検査します。各パッケージの TypeScript を別プロセスで起動するため、同時実行数は `--jobs N` で調節できます。`sh scripts/test-plgg.sh` は本体のテストです。各パッケージの `npm test` は型検査を兼ねません。

## 変更を検証する順番

公開関数の隣に `*.spec.ts` を置き、入力と戻り値を実際の部品で確かめます。本体の公開 API を変えたら `packages/plgg` で `npm run build` を実行してから利用側を検査します。ガイドは `packages/guide` で `npm run build` を実行します。両言語のコード欄をファイルにして型検査・実行してから、サイトを生成してリンクも検査します。例だけを試すには `npm run check:examples` を使います。

## レビューで見るところ

ドメインの不在は `Option`、失敗は `Result` にします。型エラーにはガードかキャスターを使い、型アサーションや検査を無効にするコメントで通しません。Prettier の幅は 50 です。設定を先に取る関数と変更前の値を保つ変換を優先し、DOM の走査などで逐次処理が必要なら理由をコメントに残します。

全体の入口は `scripts/check-all.sh` です。README とリンク、依存関係、外部ライブラリを呼ぶ場所、plggmatic のクラス名と独自 UI の有無などをゲートで確認した上で、ビルドとパッケージの検証を行います。
