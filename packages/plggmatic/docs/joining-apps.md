# plggmatic 製アプリを列でつなぐ

社内システムで作業しながら、関連する hrns の画面を右隣の列で参照できるようにしたい。社内システムが列を開き、hrns が表示してよい画面と利用者を決める。どちらも相手の認証情報や画面の実装を知る必要はない。plggpress の公開サイトも同じ仕組みに参加できる。

対象は、異なるオリジンに配信された plggmatic 製アプリ間の**閲覧**である。ログイン、承認、編集などの操作は各アプリを直接開いて行う。以下の「現行実装」はリポジトリで確認した動作を記す。設定検証とルート判定は実装済みで、版付き接続と認証アプリへの組み込みは設計案である。社内システムと hrns のホスト名、ルート、認証構成は説明用の仮定である。

## 現行実装

| 役割 | コードで確認した動作 |
| --- | --- |
| 接続の設定 | plggpress の `SiteConfig` は、列に開く相手を `partners`、自サイトを列に開ける親を `embedders`、別途 iframe に表示するウィジェットなどを `frames` として受け取る。いずれも `asOrigin` が URL の正規化済みオリジンと入力の完全一致を要求し、パス、末尾のスラッシュ、ワイルドカードを拒む。原則 HTTPS で、HTTP は `localhost` と `127.0.0.1` に限る。 |
| 配信 | plggpress のテーマは空でない一覧を空白区切りの `pm-partners` と `pm-embedders` meta に出す。`partners` があれば、`'self'`・`partners`・`frames` を許す `frame-src` も CSP meta に出す。`frames` の登録だけでは列の相手にならない。`embedders` があればビルド時に `/*` 向けの `frame-ancestors 'self' …` を含む `_headers` を生成する。効力は配信先がそれを HTTP 応答ヘッダーに反映することに依存する。 |
| 列を開く処理 | plggmatic のランタイムが起動時に meta を読む。ローカルのパスは同一オリジンの HTML を fetch し、列のマーカーが付いた要素を取り込む。外部の列は親が相手の HTML を取り込まず、相手のオリジンとパスに `pm-embed=1` を付けて iframe に開く。sandbox は `allow-scripts allow-same-origin`、referrer policy は `strict-origin-when-cross-origin`。共有 URL の `c` から復元する追加列は最大 12 件で、外部オリジンは復元時にも照合する。 |
| 親と子の照合 | 枠内かつ `pm-embed=1` で `embedders` がある子は、一覧の各オリジンを `targetOrigin` に指定し、親に `pm:title` を送る。親は `event.origin` が partner であること、`event.source` が自分の列の `iframe.contentWindow` であること、その列に記録したオリジンと送信元が一致することを調べる。タイトルを最大 120 文字のテキストとしてホスト名と表示し、`pm:scheme` を返す。子は送信元が `window.parent` かつ許可した embedder で、値が明・暗のいずれかであれば埋め込み表示に切り替える。 |
| 列での操作と失敗時の表示 | 照合後の子は横スクロールを `pm:scroll`、対象リンクを `pm:open` で親に伝える。親が開く先は自オリジンか登録済み partner のパスに限られる。メッセージに版番号はない。4 秒以内に有効なタイトルが届かなければ、親は枠を取り除き、そのページを直接開けるリンクを残す。 |

列を配置する部品も既に共通化されている。plggmatic の `shell` は `pages` から `strip` と `documentColumn` のマーカーを持つ画面を組み立てる。一方、plgg-view の `application` はモデルを描画し、同一オリジンのリンクと履歴を管理する。`navigation` を指定すれば、遷移の要求と確定通知を `ParentNavigation` に委ねられる。これは同じアプリ内の取り決めであり、別オリジンの親を認証する機能は持たない。[shell の実装](../src/Shell/usecase/shell.ts)・[application の実装](../../plgg-view/src/Program/usecase/application.ts)

plggmatic がオリジンの検証と照合を提供し、plggpress が従来の一覧を公開文書用の互換設定へ変換して HTML と配信設定に反映する。相手のオリジンが一致した後に「その相手のどのルートを開いてよいか」「誰のデータを表示してよいか」を決める処理は、現行の列ランタイムにはない。[設定と asOrigin](../../plggpress/src/SiteConfig/model/SiteConfig.ts)・[meta の出力](../../plggpress/src/theme/shell.ts)・[_headers の生成](../../plggpress/src/Press/usecase/appSpecs.ts)・[ナビゲーション](../src/Navigate/usecase/navigationScript.ts)・[マーカー](../src/Navigate/model/marker.ts)・[現在の利用手引き](../../plggpress/site/ja/joining.md)

## 提案する接続契約

### 相手とルートを片方向に宣言する

plggmatic の純粋関数 `defineJoining` は必須の自オリジン `origin` と接続設定を検証する。次は社内システムから hrns の稼働状況を開く場合の設定例である。ホスト名とパスは例示用で、`/columns/status` は個人名や業務 ID を含まない固定の閲覧用 URL とする。

```ts
// 社内システムの起動時に渡す設定
const office = defineJoining({
  origin: "https://office.example.com",
  parentRoutes: ["/"],
  partners: [{
    origin: "https://hrns.example.com",
    trust: "organization",
    paths: ["/columns/status"],
  }],
});

// hrns のサーバーと画面で共有する設定
const hrns = defineJoining({
  origin: "https://hrns.example.com",
  embedders: [{
    origin: "https://office.example.com",
    trust: "organization",
  }],
  routes: [{
    path: "/columns/status",
    access: "organization",
    mode: "readOnly",
    label: "稼働状況",
  }],
});
```

各一覧の既定値は空とする。`defineJoining(input)` は `Result<JoiningPolicy, InvalidError>` を返す。オリジンには現行の `asOrigin` と同じ制約を使い、信頼段階の競合や曖昧なルート定義は起動時にエラーにする。別アプリとして登録する partner と embedder は自オリジンから分ける。同じオリジンを共有する二つのアプリの間には、パスを分けてもブラウザーによる隔離がない。

初版のパスはルーターが認識する固定の正規パスに完全一致させる。照合前にクエリを捨てると、操作の意味が変わる URL を誤って許すおそれがある。外部入力に資格情報、クエリ、フラグメント、曖昧なエスケープやパス区切りがあれば列の対象外とし、照合後に限りランタイム自身が予約値 `pm-embed=1` を付ける。子も実際に解決されたルートとこの予約値を検査する。親の `paths` は iframe を作る前の制限、子の `routes` は自アプリが公開する範囲であり、片方への追加だけで接続は成立しない。`frames` は引き続き通常の iframe の表示先にだけ使う。

| 信頼段階 | 列として公開できる内容 | 子から親への要求 |
| --- | --- | --- |
| `public` | ログイン状態によらず同じ内容を返す公開ルート。Cookie が付いても個人向け表示に切り替えない。 | 固定の表示名と横スクロール。隣に開けるのは、親が明示的に許す公開ルートだけ。 |
| `organization` | 双方の運営者が組織向けとして登録した組み合わせ。子が自分のセッションで利用者・テナント・対象データへの閲覧権限を確認したルート。 | 公開ルートに加え、親がその送信元に明示的に許した組織向け閲覧ルートを要求できる。業務データ自体は子の中だけに表示する。 |

`mayOpenColumn(origin, path)(policy)` は登録済み partner の固定パスを照合する。`mayHonourRequest(sender, origin, path)(policy)` はさらに `requests` の同じ三項目と送信元の信頼段階を照合する。親は「どの送信元から、どの宛先へ」を判定し、表にある `pm:open` 相当の要求は個別に許可するまで無効とする。親自身の画面を開く要求にも同じ制限をかける。子はルートが要求する信頼段階と、自分の設定にある親の信頼段階を照合する。相手のメッセージによる昇格や、A が B を、B が C を信頼することによる A から C への許可は認めない。初版では列の親をトップレベルの画面に限定する。

### サーバーで埋め込みの可否を決める

親では、通常のクリック、`pm:open`、プログラムからの遷移、共有 URL の復元を同じ判定に通す。未登録のリンクを利用者が直接選んだ場合は通常のページ遷移に任せる。子から届いた未許可の要求や不正な復元項目は破棄し、自動で別ページに移動しない。

子は閲覧専用の入口を設け、編集、承認、ログインなど通常の業務画面には常に `frame-ancestors 'none'` を返す。利用者が iframe の URL を直接組み立てたり、`pm-embed` を外したりしても、この制限は同じである。閲覧用の入口では、副作用のない GET と閲覧用 API だけを使う。機密データを扱う初期 HTML は空の枠と固定ラベルにとどめ、許可した親との照合後に子が自分の API から取得する。API は要求ごとに認可する。画面遷移や履歴復元のたびにルートを再判定し、対象外ならデータ取得と描画を止め、直接開く案内に戻す。

配信には `joiningDirectives(policy, route)` が使える。`parentRoutes` は外部の枠を読み込める親画面の固定パスを列挙する。ルーターが解決したルートから CSP のディレクティブを返し、アプリのサーバーまたは配信基盤が既存の CSP に組み込む。たとえば上例で他の iframe を使わないなら、応答に必要な部分は次のようになる。

| HTML を返す画面 | HTTP 応答の CSP に含める指示 |
| --- | --- |
| 社内システムの親画面 | `frame-src https://hrns.example.com; frame-ancestors 'none'` |
| hrns の組織向け閲覧画面 | `frame-ancestors https://office.example.com; frame-src 'none'` |
| hrns のログイン・承認画面、未定義のルート | `frame-ancestors 'none'; frame-src 'none'` |

`frame-src` は親が読み込める枠の行き先を、`frame-ancestors` は子を囲めるすべての祖先を制約する。後者は HTTP 応答ヘッダーで指定する必要があり、meta や JavaScript による事後設定では代替できない。CSP はルートの業務上の意味までは検査しない。閲覧用 URL は直接応答し、保護対象の業務画面やログイン先へのリダイレクトを避ける。[Content Security Policy Level 3](https://www.w3.org/TR/CSP3/#directive-frame-ancestors)

ヘッダーは SSR、SPA の初回 HTML、エラーページ、認証ミドルウェアが返す応答まで一貫して適用する。既存の CSP を上書きせず、重複する指示や配信基盤の `X-Frame-Options` との矛盾を配信時に検査する。個人化した応答は共有キャッシュに保存しない。SPA で同じ HTML を全パスに返す場合も、閲覧用入口に専用の URL とルート別ヘッダーが必要になる。その入口からクライアント遷移で通常の業務画面に入る経路も閉じる。配信側でこの区別ができないアプリは、組織向け画面を直接開く。

### SSR とクライアント描画の組み込み方

SSR ではサーバーが検証済み設定からヘッダーと初期設定データを生成する。ブラウザーに渡すのは、その画面で使う相手、ルート名、表示用ラベルなどに限り、HTML に安全に埋め込める形に直列化する。クライアント描画では同じ形式の設定を起動時に渡す。いずれもブラウザー側の照合を同じ実装から組み立て、旧 meta と新設定を足し合わせて許可範囲を広げない。

起動 API は `attachJoining(root, policy, adapter)` とし、アプリの終了時に呼ぶ解除関数を返す。設定は配信者が管理し、リンク、相手から受け取ったメッセージ、画面上の入力を設定源にしない。設定を差し替えるときは従来の接続を解除してから新しい設定で照合し直す。

静的ページでは、マーカーが配置された後にランタイムが列の DOM と履歴を管理する。`application` を使う親では、接続アダプターが許可済みの列の追加・削除をモデルへ通知し、アプリが `shell` と外部 iframe を描画する。履歴の確定は一か所に集め、必要に応じて既存の `ParentNavigation` に接続する。再描画で同じ列の iframe を作り直さず、列を閉じたら対応するウィンドウの登録を破棄する。子側は親との照合だけでも参加できる。たとえば hrns 側が社内システムを開き返さないなら、子に列の履歴管理は要らない。

### 認証と Cookie

別オリジンでも、同じスキーム・同じ登録可能ドメイン配下なら同一サイトになり得る。接続先の完全一致にはオリジンを使い、Cookie が送られる条件は別に評価する。クロスサイトの iframe では `SameSite=Lax` や `Strict` の通常のセッション Cookie は送られない。`SameSite=None; Secure` を指定しても、ブラウザーの third-party cookie 制限や利用者設定で使えない場合がある。既存のセッション Cookie の適用範囲を、列のために一律に広げる設計は採らない。[HTTP Cookie の SameSite 規則](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis#section-5.2)・[Storage Access API の利用背景](https://privacycg.github.io/storage-access/#intro)

セッションを利用できない場合、子は機密情報を含まない案内だけを表示する。親の列見出しには初めから「hrns を直接開く」リンクを置き、利用者の操作で検証済みの閲覧 URL をトップレベルで開く。そこで hrns が普段のログインと認可を行う。子から任意のログイン URL や戻り先を受け取らず、sandbox のポップアップ・親画面遷移の許可も追加しない。ログイン後に列を開き直しても Cookie が使えなければ、そのままトップレベルで閲覧できる。

`Partitioned; Secure` の Cookie（CHIPS）はトップレベルサイトごとに別の状態を持つ。hrns を直接開いたときのセッションを社内システムの枠へ引き継ぐ手段にはならない。初版では枠専用セッションの新設も、Storage Access API による非分割 Cookie へのアクセス要求も前提にしない。後者を必要とする場合は、対象ブラウザー、利用者操作と許可、sandbox の追加権限、拒否時の動作を個別に評価する。[CHIPS の分割単位](https://privacysandbox.google.com/cookies/chips)・[Storage Access API の仕様案](https://privacycg.github.io/storage-access/)

親子間でアクセストークン、セッション ID、認可コード、CSRF トークンを渡さない。URL、フラグメント、共有 URL の `c`、タイトル、`postMessage` のいずれにも載せない。組織向け列の所在は初版では親のメモリ内だけに保持し、共有 URL や永続履歴に保存しない。親が表示する名称には設定済みのラベルと実際のオリジンを使い、子の `document.title` に含まれ得る氏名・案件名を送らせない。

### postMessage の版管理

現行の版なしメッセージは既存の公開サイト用として扱う。新方式ではメッセージにプロトコル名、メジャー版、種別を付ける。親が iframe の読み込みごとに新しい照合値を発行し、期待するオリジンだけに開始要求を送る。子は直接の親とそのオリジン、自分のルートを照合して同じ値と対応機能を返す。親も送信元ウィンドウ・オリジン・照合値を確認し、双方の設定で許した機能だけを有効にする。この値は直前の読み込みへの応答を識別するためのもので、利用者認証には使わない。枠の再読み込み、遷移、削除時には成立済みの接続を失効させる。

各メッセージについて、方向、必要な信頼段階、必須フィールド、値・長さ・頻度の上限、受信時の効果を定める。たとえばテーマは親から子への明・暗の二値、横スクロールは子から親への有限の数値に限る。開く要求は受信のたびに送信元と宛先ルートを照合する。未知の版・種別、不正な値、合意していない機能は無視する。共通の版がなければ直接リンクに戻し、組織向け接続を版なし方式に格下げしない。[HTML Standard のメッセージ送受信時の検証](https://html.spec.whatwg.org/multipage/web-messaging.html#security-postmsg)

新しい任意機能は明示的な合意と両側の受信テストを条件に追加する。既存の意味や必須項目を変えるときはメジャー版を上げる。「選択中のレコードを送る」「親が代わりに API を呼ぶ」といった要求は、閲覧の契約を超えるため別途設計する。任意のコマンド、HTML、資格情報を運ぶ汎用メッセージは設けない。

## 想定する攻撃と防御

以下は導入先に対する脅威の想定であり、社内システムや hrns にこれらの不備があるという調査結果ではない。

| 想定する攻撃・失敗 | 防御と、なお残る条件 |
| --- | --- |
| 第三者がログイン済みの業務画面を透明な枠で覆い、利用者に承認ボタンを押させる | 子の業務画面とログインには `frame-ancestors 'none'`。許す入口には閲覧 UI だけを置く。許可済みの親は枠の外側を自由に描けるため、組織向けの親自体を運営者が審査する。 |
| リンク、共有 URL、子からの要求を通じ、削除・承認・ログアウトを読み込みだけで実行させる | すべての入口で宛先ルートを照合し、状態変更を GET に実装しない。更新 API は通常画面でもサーバー側認可、CSRF トークンや Origin 検証で保護する。sandbox のフォーム制限だけでは子のスクリプトによる通信を防げない。 |
| 公開サイトの列から、隣にある社内アプリを利用者の権限で操作する | 送信元の信頼段階を列ごとに保持する。公開列から組織向けルートへの要求は拒否し、兄弟のウィンドウからの応答も捨てる。子の API が利用者・テナント・対象ごとに再認可する。 |
| 別のウィンドウや遷移前の文書が正規の子を名乗る。拡張メッセージを繰り返し送る | 受信ごとにオリジン、ウィンドウ、接続の版と照合値を検査する。種別と頻度を制限し、閉じた列の要求は受け付けない。 |
| 認証切れを装って枠に資格情報を入力させる。連携用 URL や表示名を経由して秘密を持ち出す | ログインは親が保持する固定先からトップレベルで開始する。業務列は固定ラベルを使い、資格情報・個人別の URL を親や履歴に渡さない。Cookie を利用できない場合も同じ導線を使う。 |
| 動的なエラー応答、SPA の共通 HTML、キャッシュにより、拒否対象の画面や別利用者の内容が表示される | 配信経路の既定は埋め込み拒否とし、許可ルートの実応答だけに例外を付ける。個人化データのキャッシュを分離または禁止し、401・403・404 と直接アクセスも配信試験に含める。 |
| 許可済みの相手が侵害され、正しいオリジンから偽の表示や正規形式の要求を送る | オリジン照合だけでは侵害を識別できない。親は出所を枠の外に表示し、許した閲覧以外の要求を拒む。相手単位で登録とヘッダーの許可を撤回し、稼働中の列も閉じる。既に相手側で漏れた情報は回収できない。 |

## 段階的な導入

1. **公開サイトの互換性を確かめる。** 最初に plggmatic に設定検証と判定関数を作り、既存の版なしランタイムで使うオリジン照合も同じ実装から生成する。plggpress をその最初の利用者とし、従来の一覧を公開文書用に明示した互換設定へ変換する。既存サイト同士で開く・戻る・4 秒後の直接リンクが動き、meta と `_headers` の出力条件が変わらず、`frames` だけの相手を列にできないことを確認する。
2. **認証不要の別アプリで一方向を通す。** 新方式の親子照合、固定の閲覧ルート、ヘッダー生成を実装し、SSR とクライアント描画の組み合わせで試す。通常のクリックと再描画で列が二重に開かず、未登録の親・ルート、未知の版、直接 iframe に入れた編集画面がすべて拒否されることを実ブラウザーで確かめる。
3. **組織内の一画面で試行する。** 社内システムから hrns の担当者が選んだ閲覧用入口だけを開く。権限やテナントの異なる利用者、セッション切れ、third-party cookie の拒否、戻る操作を試す。権限のないデータが届かず、利用者が直接開く導線で作業を続けられ、共有 URL とログに利用者データが残らないことを導入条件とする。
4. **接続を運用単位で増やす。** 双方で管理者と失効手順を決め、サーバー側の公開停止、設定再読込と既存 iframe の破棄、配信キャッシュへの反映までを試す。新しい相手、逆方向の接続、追加ルートはそれぞれ個別に登録する。

## 未決事項

- **最初に公開する業務画面。** hrns の担当者と社内システムの運営者が、副作用のない入口、表示項目、親に開示できる固定ラベルを選ぶ。レコードごとの URL や動的パラメーターが必要なら、その識別子を誰が知ってよいかを先に決める。
- **認証とブラウザーの対象範囲。** 本番のサイト配置、Cookie 属性、管理対象ブラウザーを確認し、トップレベルへの誘導で業務を完結できるかを試す。枠内セッションが必須と判明した場合に限り、分割 Cookie の確立・失効方法や Storage Access API の採否を再検討する。
- **配信と失効の責任者。** SSR サーバー、認証基盤、CDN のどこで最終ヘッダーを保証するか、緊急停止が開いたままの画面まで届く期限を決める。期限を保証できるまでは組織向け接続を試行先に限定する。
- **互換期間と履歴の扱い。** 公開サイトが版なし方式を必要とする期間を確認する。組織向け列を再読み込み後にも復元したい場合は、履歴に残せる情報と再認可の方法について、初版のメモリ内保持とは別に合意する。
